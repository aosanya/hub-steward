# Phone app: a guide for contributors

`code/app` is the member's phone app: React 18, React Router 6 and Vite, with Vitest for tests (`code/app/package.json`). It holds no data. Every screen reads and writes through the Wakala API. For the run commands see the [running guide](../build/02-running-it/README.md); for languages see [languages.md](languages.md).

## Where things are

Everything is under `code/app/src`.

| Folder | What it holds |
|---|---|
| `tabs.ts`, `routes.ts`, `App.tsx` | The bottom bar, every screen's path, and the route table |
| `agency/` | Which agency is open (`open.ts`) and which modules it has switched on (`modules.ts`) |
| `wakala/` | The API client: runtime address (`config.ts`), token (`token.ts`, `renewal.ts`), the signed-in person (`me.ts`), tool calls (`mcp.ts`) |
| `entry/` | Sign-in, the agency list, the language picker and the words (`words.ts`, `swahili.ts`, `magyar.ts`, `language.ts`) |
| `home/`, `started/`, `inbox/`, `pages/` | Home's cards (`home/HomeOptions.tsx`), the Start rows, the Ongoing reads, the Notifications page and the count behind the bell, and the page components |
| `chat/`, `forms/`, `groups/`, `people/` | One folder per feature: its API calls (`api.ts`) and its tests |
| `market/`, `buy/`, `sell/`, `supply/`, `coordinator/` | The market: products and prices, buying, selling, shops' offers and orders, the coordinator's group order and payments |
| `apps/` | The chat-workflow thread screens |
| `backlogs/`, `backlogBoard/`, `backlogPage/`, `backlogManage/`, `backlogAccess/`, `smartBacklog/`, `sendToBacklog/` | The Backlogs screens: the lists and the issue page, the Kanban board, a backlog's page, adding and editing backlogs, who has access, smart backlogs, and selecting issues to send to a backlog |
| `ui/` | The shared components |
| `journeys/` | The walk tests and their test support |

## Routes and tabs

- `tabs.ts` defines one bottom bar, `mainBar`: Home, Chat and Notifications (decisions 154 and 155), drawn by `TabBar` on every screen. The Notifications button carries the unread count and the bell icon; Start, Ongoing and Backlogs are not buttons of the bar, Home opens them, and they and every screen a row opens keep the bar with none chosen. `TabBar` still records the side a person reached, Start or Ongoing (`rememberSide`, `sideOf`, `sideReached`), and a screen opened from a row uses `doSomethingBackPath()` for its back button, which goes to that side, and Start when none was reached. A tab's path is `/a/<agency id>/<segment>` (`tabPathIn`).
- Each tab carries an `icon` (an `IconName` of `ui/Icon.tsx`), not a text glyph: Home is a house, Chat a message bubble, Notifications a bell, Start a play triangle, Ongoing a clock and Backlogs a list. `Icon` draws a 24 by 24 line icon in `currentColor` at `1.5rem` (the `.icon` rule in `app.css`), so the chosen tab takes the accent colour and the others the muted text colour; add a drawing to its `shapes` table to add a name.
- Backlogs is not a button of the bar. Its card on Home shows only when the agency has the `taskmanager` module (`hasModule` with `taskModule`, `agency/modules.ts`) and the person can see a backlog. The bar is always three buttons of equal width, so nothing is reserved while the modules are read (`ui/tabBar.test.tsx` checks that the bar has no `reserve` class).
- The Chat list is one row for every group the signed-in person belongs to (`actor_list_my_groups`), the way WhatsApp lists its chats: the group's name, the newest message and its time, the unread count, newest activity first. A group nobody has written in yet is still listed, last and by name, with "No messages yet"; tapping it opens the empty threads page, which offers Start a thread. A group whose thread list could not be read is left out, and the tab says it could not be loaded only when every group failed (`chat/api.ts` `roomsOf`, `pages/chat/ChatPage.tsx`).
- A group's room has the three-part bar: the Chat back label at the left, the group's name centred, the menu at the right. The thread's name is a plain pill under the bar. The threads sit in one collapsible Card headed "Threads · N", open at first, whose rows are the same thread rows the threads page uses (`chat/rooms/ThreadRows.tsx`). The threads page has the same bar with the room's name as the back label; with no threads it shows the empty card with Start a thread inside it. The writing box stays pinned at the bottom, at the standard content size (`chat/rooms/RoomThreadPage.tsx`, `RoomThreadsPage.tsx`).
- The assistant page (`src/assistant`) has a Chat | Results tab strip. What the model reads through `taskmanager_task_list`, `taskmanager_task_pending` and `taskmanager_task_read` is kept as typed lists (`results.ts`, one for every call, newest first), not drawn in the chat: the chat shows an entry row for each list (title and count), and the Results tab shows the list the dropdown has chosen as shared issue rows in a Card. Tapping an entry selects exactly that list; new data puts a dot on the Results tab while Chat shows; a list longer than fifty rows has Show more, and a list the tool cut says how many of the total it holds.
- The assistant page answers one message at a time. While an answer is pending the assistant side shows three pulsing dots (still dots when the person prefers reduced motion) with Looking it up and, when a tool runs, its step in plain words (`stepWords` in `assistant/api.ts`). The writing box clears at once and keeps the cursor, and the send button stays enabled: a message written meanwhile is added to the conversation as a bubble marked Queued, with a remove cross until it is sent, and is sent on its own, in order, with the conversation so far when the answer arrives (`assistant/queue.ts`, mirroring the console chat's queue: its words Queued and Remove from the queue). A request that fails or takes over 60 seconds pauses the queue and shows That did not work. Try again. with a Try again button; the rest stay queued. Leaving the page keeps nothing queued. The Chat list pins the assistant as its first row, and Join a group is a button after the last row, in the empty card when there are no groups.
- The assistant page speaks with the description of the agency's Triager role, read from the hub each time it asks (`src/assistant/triager.ts`): the newest production publication from `agency_list_publications`, then the role named Triager from `agency_list_roles` for that publication's draft. The page adds its own closing lines (read tools only, no chat posts or cards on this page, issues go to the Results tab). When the person may not read publications, or the hub has no production publication or no Triager, it falls back to the page's own shorter prompt in `src/assistant/api.ts`.
- An open chat hides the bottom bar (decision 50): the thread, the list of threads on top of it and an ask opened from it pass `tabless` to `Shell`; the list of chats keeps the bar. An agency's old `/started` address, with or without the agency, goes to Ongoing.
- The home screen is `/a/<agency id>/home`, headed Home (decisions 154, 157 and 158). It holds a strip (`home/NeedsYouStrip.tsx`), You have N things to do, which opens the Needs you section of the Notifications page, above the cards Start, Ongoing and Backlogs (`home/HomeOptions.tsx`). The strip shows the one count of the bell, is not drawn at 0, and shows no number before the reads answer or after one fails. `App.tsx` mounts Home as `NotificationsPage` with the strip and the cards passed as `above`, so the page's sections follow the cards under the heading Home. Only the cards the agency and role have are drawn, in that order, each as its own card with its icon and a chevron (decision 156); a role that only uses backlogs sees its backlogs in their place, the last one opened first (`home/lastBacklog.ts`). An agency's address, a sign-in and choosing an agency all land on Home. Start is `/do-something`, headed Start a task, and its rows are in `home/StartRows.tsx`. Ongoing is `/ongoing`, headed Your tasks (`pages/HomePage.tsx`, `pages/started/Ongoing.tsx`); the backlog screens are mounted under `/backlogs/*` by `BacklogsRoutes`. The old `/inbox` and `/a/<agency id>/inbox` redirect to Home (`retiredInboxRoute`) and keep their query string and router state. A back button that means Start or Ongoing uses `doSomethingBackPath()` (or `doSomethingPath()` for Start itself), never `"/"`, which is the home screen.
- Ongoing opens on the Live tab (`started/api.ts` reads the rows with `startedAnswerOf`): the tasks the member has begun, the ones waiting on her first under Needs you and the rest under With others, each row saying why or what it waits on. Done (`pages/started/DoneTab.tsx`, reads in `started/done.ts`) keeps what finished, read-only and newest first: closed and called-off group orders, delivered and cancelled orders, and the forms she sent. It reads one page of 20 for each of the five sources when Done is opened, not before, and Show more reads the next page of the sources that filled theirs. An order row opens its page and a sent form is a plain row. A source that fails is named (Some of your finished tasks could not be loaded, Try again) while the others show; when every source fails the tab says Your finished tasks could not be loaded. A delivered order appears only once something sets `delivered_at` (ISS-154), and `steps/sent.ts` is not rebuilt from the server list because that would hide a start step that can be sent again.
- The Notifications page is `/a/<agency id>/notifications` (`pages/NotificationsPage.tsx`) and has two sections. Needs you comes first (`inbox/NeedsYouSection.tsx`): the steps waiting on the member (`StartWaitingRows` in `coordinator/start/Waiting.tsx`), the invitations, and the notifications that announce something waiting, listed in `waitingEvents` in `inbox/needsYou.ts`. An issue assigned to the member is a row of its own (`inbox/AssignedIssueRows.tsx`, read by `inbox/assignedIssues.ts` as the open issues whose `assigned_to` is the member's actor, only when the agency has the task module), listed by code and title, opening the issue; its `task_assigned` notification, worded An issue was assigned to you, is left out while the issue is listed (`inbox/issueCount.ts`) and the issue is counted once, in the Home strip and the bell. Updates comes second (`inbox/UpdatesSection.tsx`): the news, one row for each notification (`inbox/NoticeRow.tsx`). Mark all read clears Updates only. When both sections are empty the page shows the You are all caught up card. When the notifications or invitations read fails because the agency has no comm module (a tool-level answer, not a server error or a lost connection), the page shows its calm empty card; only a real outage (a server 5xx, a lost connection, a refusal) shows the failure with Try again (`inbox/outage.ts`).
- A form step (`steps/StepPage.tsx`) keeps a half-filled form on the phone, by agency, step and run (`stepDraftKey`, `loadDraft`, `saveDraft` and `clearDraft` in `pages/forms/answers.ts`, written through `storage/kept.ts`, which does nothing when the browser blocks storage), and drops it only when the server confirms the send. Each opening of the form makes one send key (`newSendKey` in `steps/api.ts`), so a repeated Send is the same send and a 409 reads as sent; Send reads Sending while it is in flight, and a send over `sendTimeoutMs` (20 seconds) says Try again. A sent step is kept the same way (`steps/sent.ts`, under `hs-sent-steps`) and survives a reload; its Sent row in `home/StartRows.tsx` names the role whose turn is next, Next: <role>, or says Done (`afterWords`). A refusal is worded by `refusalWords` in `steps/api.ts`: a step for another role offers Go to Start, a step not ready or already sent offers Go to Ongoing.
- A read that fails is never shown as empty. Start and Ongoing say Your tasks could not be loaded, and Ongoing says Some of your tasks could not be loaded above the rows it did get, each with Try again; Chat says Chat could not be loaded and Loading Chat while it reads; a step that cannot be read says This task could not be opened with Try again, and a step that is gone says This task has closed. The Notifications page and Home say Home could not be loaded with Try again when a notification or invitation read fails for any reason except an agency that does not serve the tool (`isModuleOff` in `inbox/outage.ts`).
- Every unread row in Updates has a checkbox (`SelectableRow` in `ui/ListRow.tsx`; read rows get a blank space of the same width so the rows line up). Ticking one changes Mark all read to Mark read, which marks only the ticked rows through `markIdsRead` in `inbox/useNotifications.ts`; unticking them all brings Mark all read back, and the ticks drop when a row stops being unread. Tapping a row still opens its subject; the box only selects.
- One count, the same on the Home strip and the bell (decision 158): the things waiting on the member. `needsYouCount` in `inbox/needsYou.ts` adds the steps waiting on her (the group order's Create step, which can always be started, is left out), the invitations and the unread notifications that announce a waiting thing. `useNeedsYou` (`inbox/useNeedsYou.ts`) reads the three and answers `count`, which is `null` until all three are read and after any one failed, so a failed read never shows as 0. `thingsToDoLabel` (`inbox/thingsToDo.ts`) turns it into the number on the bell, capped at 99+ by `unreadLabel` (`chat/unread.ts`). Unread news is a dot on the bell with no number (`newsUnread`). The count is of the open agency only, and the lists read again when the app regains focus (`inbox/regainFocus.ts`).
- `routes.ts` builds the path of 20 agency screens from one definition each: `screen("/market/:productId")`. Call `routes.product.path({ productId })`; never write the string by hand. `pattern` is `/a/:agencyId` plus the path, and `retired` is the old path without the agency.
- `App.tsx` registers each `pattern` inside the `/a/:agencyId` block, and registers every `retired` path as a redirect to the open agency (`ToOpenAgencyScreen`), or to `/agencies` when none is open.
- Many screens are not in `routes.ts` yet: `App.tsx` declares `/buy/wanted`, `/my-orders`, `/sell/...`, `/asks`, `/offers`, `/orders`, `/coordinator/...` and `/group-orders` as plain paths outside the agency block.
- The open agency lives in memory and in `sessionStorage` under `hubsteward.openAgency` (`agency/open.ts`).

## Talking to the API

- **Address.** `wakala/config.ts` fetches `/config.json` once. `public/config.json` holds `{"wakala":"http://localhost:8082"}`. With no file the app uses the same origin and `/mcp`.
- **Builds.** `demoConfig.ts` writes `config.json` into `dist/` from `HUBSTEWARD_WAKALA_URL` (`vite.config.ts`). `npm run build:demo` stops when the variable is unset (`scripts/build-demo.mjs`).
- **Token.** The bearer token is kept in `localStorage` under `hubsteward.token`. `authHeaders()` returns `Authorization: Bearer ...`, and `renewal.ts` swaps an expiring token by posting to `/auth/refresh`.
- **Password sign-in on a local hub.** The Sign in screen also shows an email and password form when `entry/localHub.ts` finds that both the page and the hub address are on this machine (a loopback host); a deployed app never shows it. `entry/passwordSignIn.ts` posts the address and password to the hub's `/auth/signin` with the cookie, and a good answer sends the person to the app home. A wrong pair says so, and a locked-out address says the hub is busy.
- **Calls.** Features call `callTool(hubId, tool, args)` in `wakala/mcp.ts`. It adds `instance_id` from the open agency. Reads are reused for 10 or 60 seconds, and any other call clears them.
- **Clients.** A feature's `api.ts` defines a client type and a live client. `forms/context.tsx` shows the pattern: a provider and a hook, so a test hands the screen a fake client.

## Languages

- The picker lists nine languages (`languages` in `entry/words.ts`), but only English (`words.ts`), Kiswahili (`swahili.ts`) and Hungarian (`magyar.ts`) have words. Any other code falls back to English (`wordsFor` in `entry/language.ts`).
- The choice is kept in `localStorage` under `hub.language`.
- Not all text goes through the words yet: `pages/forms/FormsPage.tsx` writes "Closes this week" in the component. Put new text in `words.ts`, and add its Kiswahili to `swahili.ts`, whose type is `Words`.

## Tests

- Run all with `npm test` (`vitest run`), or one file with `npx vitest run src/routes.test.tsx`. The environment is jsdom, and `src/test-setup.ts` points the runtime address at `https://wakala.test`. There are 255 test files.
- `routes.test.tsx` checks that every path is built from its definition and keeps its retired path.
- `journeys/*.walk.test.tsx` and `journeys/backlogs/*.walk.test.tsx` (19 files) render `<App />` in a `MemoryRouter` and walk a journey screen by screen. `journeys/inAgency.test-support.tsx` has `stubWakala` (it stubs `fetch` and records each tool call), `everyCallNames` (every call names the open agency) and the farmers' and riders' agencies.
- A bug fix needs a test that fails without it (see [CONTRIBUTING.md](../../../CONTRIBUTING.md)).

## Add a screen

1. Add the API call to the feature's `api.ts` with `callTool`, behind its client type.
2. Add `name: screen("/path/:id")` to `routes` in `routes.ts`. `allScreens` picks it up, so its retired redirect is registered for you.
3. Write the page under `pages/<area>/`, wrapped in `Shell` (`title`, `onBack`, `action`, or `tabless` to hide the tab bar).
4. Add `<Route path={routes.name.pattern} element={...} />` inside the agency block in `App.tsx`.
5. Link to it with `routes.name.path({ id })`, and add a row to the table in `routes.test.tsx`.
6. Add the text to `words.ts` and `swahili.ts`, write a test, and update the matching journey page.

## Reuse these

Use `ui/` before writing markup: `Shell` (with `TopBar`, `ScreenHead`, `TabBar` and the account `DrawerFrame`), `LoadState` (`EmptyCard`, `LoadingLine`, `LoadFailed`), `Button`, `Card`, `Chip`, `ListRow` and `Rows`, `Segmented`, `Field`, `ChoiceRow`, `SearchSelect`, `SectionHeading`, `JoinForm` and `ProductRows`. Do not add a second copy.

`Card` is the one card surface. `<Card>` alone is the plain card and `<Card empty>` the centred empty one. `<Card title="...">` adds a header row with the title; add `collapsible` to make the header a button with a chevron (`aria-expanded`, Enter and Space toggle) and `defaultOpen={false}` to start closed. The content sits in a body below the header, so a footer can be added later without changing callers. In a chat thread, put a card in a `rm-slot` wrapper for its width and side, never a second copy of the surface.

## Look and feel in the code

- The root is `font-size: 112.5%` (`tokens.css`) and the body is `1rem`. Every font size in `app.css` is in `rem`; there are none in pixels.
- Touch targets are at least `3rem` high (`.bar`, `.btn`, `.input`, `.tab` in `app.css`), and list rows `3.5rem`.
- The top bar is sticky, and back is a plain `‹`. An empty list is a `Card empty` with a sentence, not a blank page.
- No comments in code. Put an explanation in `documentation/`.

## Common mistakes

- Writing an agency path by hand. It breaks when the path changes: use `routes.x.path()`.
- Calling `fetch` for data. Use `callTool`, so the call names the open agency and the cache clears on a write.
- Hard-coding text in a component, so it never reaches the Kiswahili words.
- Testing against the live client. Pass a fake client or use `stubWakala`.
- Forgetting that the app has no server of its own: with no API at the address in `config.json`, every page after sign-in fails.

## Issues on the Backlogs screens

- One card draws an issue everywhere: `backlogs/IssueCard.tsx` (with `backlogs/IssueTitle.tsx`, and `sendToBacklog/SelectableIssueRow.tsx` for the tick-box rows). The code (the first word of the title when it looks like an id, `DEV-009`) is in the accent colour, the title is plain text at `--content` (one number in `tokens.css` for body text on these screens), two lines of title at most. Under the title an interactive row (lists, board cards, Waits on, Waited on by) shows the lighter line (`IssueLine` in `backlogs/IssueTitle.tsx`): one grey line with the repo and the backlog, and a Blocked chip only on an issue that is blocked; the repo is named once, by its last path segment (`projects/x` reads `x`), and the backlog is left out when it reads the same. A static row (the top of an issue's page) keeps every tag as a pill (`IssueTags`). Variants are by prop: interactive or static, with or without a chevron.
- The repo, the backlog and the Blocked chip on a row are filters on the rows and cards of the lists that have a filter (All issues, a backlog's list, the board): tapping one adds the tag, tapping a chosen one removes it, and neither opens the issue. Ready is no longer drawn on a row, so it is not a tap-to-filter chip. In the issue page's top and in Waits on / Waited on by the tags are plain pills.
- The list and the board share one pinned filter bar (`backlogs/FilterBar.tsx`, sticky under the header): the search field (`ui/SearchBox.tsx`), the count and the chosen tags. Every typed word must appear in the code, the title or a tag, case-insensitive, together with the tag filter, kept in the address as `q`. The count reads `12 of 1661 issues` while narrowed.
- An issue's page: header `‹ All issues`, the code in the middle; the static row, the description as markdown (`ui/Markdown.tsx`, no library) in a card, Waits on and Waited on by as rows of one card, and the loader's `Read from` lines apart under Source.
- The header (`ui/TopBar.tsx`) is three parts when a screen passes a back label: the label at the left, the title centred, the menu at the right.

## Smart backlogs, Select and send, and who may edit

- **Two kinds of backlog.** A backlog with steps holds issues and shows a board. A smart backlog has no steps and no issues of its own: it is a saved set of rules, and what it lists is whatever the rules match now, narrowed to what the caller can see. The Backlogs screen lists both; a smart one has a Smart pill and only its count (`backlogs/BacklogsPage.tsx`). Add a backlog asks first, in a bottom sheet (`ui/Sheet.tsx`), Backlog with steps or Smart backlog.
- **The rules screen** (`smartBacklog/RulesScreen.tsx`): a name, Match all or any, one row for each rule (field, operator, value, remove), Add a rule, a live count of the issues that match, and Create. The nine fields and their operators are in `smartBacklog/fields.ts` (Tag, Mark, Backlog, Step, Priority, Title, Description, Waits on, Last changed); there is no limit. The routes are `new/smart`, `:id/smart` and `:id/rules` under the Backlogs path (`smartBacklog/paths.ts`), and the calls are `smartTools` in `smartBacklog/api.ts`.
- **Opening one** (`smartBacklog/SmartBacklogPage.tsx`): the rules read back, the count and the issues, with no List or Board switch; a person who may manage backlogs sees Edit rules. A smart backlog that matches nothing is an empty card with Edit rules inside it. Saving the same rules twice is refused with a 409, and the screen links to the backlog that has them.
- **Select and send** (`sendToBacklog/`): Select in the top bar of a list, of the Kanban board and of a smart backlog's list turns the rows into rows with a tick, with a count in the title, All and Cancel; a Send to backlog bar opens a sheet of the backlogs with steps the person may move into (the `level` on `taskmanager_backlog_list`; edit counts as move), and each issue goes to the target's first step through `taskmanager_task_move_to_step`. It stops at the first refusal and says how many went through; a successful send reloads the list. An opened issue has a Send to backlog button for the one issue. The tick box is `SelectionBox` in `ui/ListRow.tsx`. There is no Undo.
- **Three access levels** (`backlogAccess/`): the Access screen shows Can see, Can move and Can edit for each group, each including the one before, and a cross that takes a group's access away; there is no No access segment. The Product owner group is fixed at Can edit, and a smart backlog offers only Can see and Can edit. Can edit gives the Backlog manager role (`backlog_manager`), as Can see gives Backlog member and Can move gives Backlog worker.
- **Tools** (all `taskmanager_` plus the name): `backlog_create` takes `steps` or `rules`, `backlog_rules_set` changes a smart backlog's rules, `backlog_rules_count` counts what rules match without saving, and `backlog_list` carries `kind`, `rules`, `level` and, for a smart backlog, `issues` as the live count.
- **Save as smart backlog from a filter** (`smartBacklog/fromFilter.ts`, `rulesKey.ts`): on a list with a tag chosen or a search typed, a person who may manage backlogs sees a quiet Save as smart backlog button under the count. It opens the rules screen already filled: a Ready or Blocked tag becomes a Mark rule, a backlog name a Backlog rule, any other tag a Tag has rule, and each typed word a Title contains rule, matched on all, with a name made from the filter that can be edited. When a smart backlog with the same rules already exists (compared the way the server normalises them), the button is replaced by an Open link to it.
- The design is in [smart-backlogs.md](../../2.%20design/technical-spec/backlog-app/smart-backlogs.md) and its [mockups](../../2.%20design/mockups/app/index.html); what was built is in the hub-steward-swe repo, `documentation/3. implementation/smart-backlogs.md`.
