# Design requests: the hub console

These files are static pages built in a dark, amber visual style; open `index.html` first, then any file in a browser. The set started as the Model key journey and is now the whole hub console (earlier notes and the file `studio.css` call it the studio): every page of the sitemap, each state a full-window screen under a monospace caption, all sharing one stylesheet, one side bar and one chat column. The side bar of every file links to the other files, so the set can be clicked through.

## How these files are made

These HTML files were generated from `_generator/`, which is not in this repository, so here they are edited by hand. The generator held: a shared kit (stylesheet, icons, components, chat components), the sitemap, and one page module per area. Run `python3 -I build.py --static` inside `_generator/` to rewrite every file; every page draws its menu, header and chat box in place, needs no script and links the one stylesheet, `studio.css`; `--out <dir>` builds into a scratch folder and `--only pages_a,pages_b` builds only some modules. The generator's README, `_generator/README.md`, has the full component list, the rules for adding a page module and the link and chat conventions.

## Design principle: shared components

The console is composed of shared components: each piece is built once and pages only supply their content. A page supplies only its title, its one primary button, its content and its chat conversation; the header strip, the menu and the chat column are written once and never drawn by a page, and the real build (the console in code/console) follows the same split. [`components.html`](components.html) is the component catalogue, generated like every other file: one screen per group (the anatomy of a page, the layout components, the page components, the chat messages, the form objects and the five themes), each component drawn live with its real kit function and labelled with its name. The groups are Layout (`shell`, `header_strip`, `hub_switcher`, `menu`, `title_row`, `chat_column`, `from_chat`), Page (`stats`, `table`, `detail`, `setting_rows`, `form_card`, `action_card`, `tabs`, `filter_bar`, `empty`, `draft_bar`, `notice`), Chat messages (`msg_*`), Form objects (`field_*` and `form_object`) and Themes.

A page that edits the agency's definition (Profile, Goals with its goal and objective pages, Roles, Risks) shows the draft bar at the top of its content area, under the title row. Approved changes pile up in the agency's open draft, and agents and members keep using the published version, so the bar says how many changes wait and offers Publish; publishing runs the validation scan and makes one new version for all of them. Its Publish button is the one other filled accent button on those pages. Its five states are drawn in the catalogue and in the five themes: none (nothing is drawn), pending ("3 changes not published", See what changed, Publish), publishing ("Checking the agency before publishing", the button reads Publishing), failed ("Nothing was published", the problems listed one per line, the button reads Publish again) and published ("Published as version 4"). The agency pages show the pending bar in `agency/agency.html`, `agency/agency-detail.html`, `agency/roles.html`, `agency/profile.html` and `agency/risks.html`, with publishing and failed on `agency/roles.html`, and "See what changed" opens `agency/agency-draft.html`, the answer to "What is not published?" in the content area. The Approvals detail of an approved agency change (`work/approvals-agency-change.html`) carries the quiet chip "Not published yet" with a link to Goals. The tools are the agency's own (`agency_list_drafts`, `agency_list_issues`, `agency_publish_agency`, `agency_list_publications`); the list of what the draft changed, with who approved each change and when, is Proposed.

A form is drawn from the tool's input schema, never hand-built: `form_object` turns the JSON Schema of an MCP tool into a form, with a field object for each type, a required mark, an error line and a footer with Submit, Cancel and, for a pending write, "Pending approval".

Every row action and title link is a real link to the screen it opens (`@/file#sN`, with a tooltip "Opens: ..."): an "Open" on a list row goes to the detail screen in the same file, a related thing to another page's screen, a form to the next screen of its flow, and a chat navigation button to the other page's landing. A link whose target is not drawn says so in its tooltip, and the build lists every dead link as a warning for the page owners.

## Folders and files

`index.html` is the design index: the three agencies, the sitemap as a nested list with the agencies whose menu has each page, then one card per page with its route, file, number of screens and the journeys it serves; a page whose file is not generated yet is shown as planned. Every file below lives in a folder named for its area, and links between files are written with the `@/` token so they work from every folder.

- `entry/`: `sign-in.html`, `create-hub.html`, `hubs.html`, the pages before a hub is open.
- `status/`: `status.html`, `hub-switcher.html`.
- `agency/`: `profile.html` (the agency's own identity: name and purpose), `agency.html` (Goals) with its goal and objective pages `agency-detail.html` and `agency-add-objective.html`, `roles.html` (the agency's own roles), `risks.html`, `agency-draft.html` (what the draft changes).
- `people/`: `members.html` (Users), `groups.html`, `agents.html` and its detail pages `agent-edit.html`, `agent-instructions.html`.
- `work/`: `approvals.html` and `approvals-agency-change.html` (an approved agency change, not published yet), `operations.html` (the Overview) with its sub-menu pages `operations-network.html`, `operations-activity.html`, `operations-alerts.html`, `farm-orders.html`, `produce.html`, `equipment.html`.
- `knowledge/`: `documents.html`.
- `studio.css`: the one stylesheet every page links to.
- `settings/`: `general.html`, `models.html`, `model-add.html`, `model-edit.html` with its tabs `model-limits.html`, `model-users.html` and `model-usage.html`, `model-template.html`.
- `flows/`: `step-01-set-the-key.html`, `step-02-test-the-key.html`, the Model key journey followed across pages.
- `_generator/`: the generator and its README.

The area pages are drawn by their own page modules, so the files that exist at any moment are those listed as drawn on `index.html`.

## Three of the eight agencies, one console

The demo has eight agencies ([demo](../../../../demo/)); these pages draw three of them, each its own hub with its own template: the Siaya Community Computer Lab, the Siaya Farmers' Group and the Siaya Boda Boda Riders (`demo/siaya-lab`, `farmers`, `boda-boda-riders`). The console shows one agency at a time, and its menu follows that agency's template, so a page appears only in the menus of the agencies that have it: Approvals, Operations and Documents in the Lab and the Riders, Equipment in the Riders, Farm orders and Produce in the Farmers. The Farmers' group is the hub the Model key walk uses. The Lab and the Riders in the hub switcher are the real demo templates drawn as the manager's other hubs: example hubs, with the roles, groups, goals and workflows of their templates. The hub switcher lists all three agencies with a kind chip and a state, a check on the open one, an Open link to each other agency and New hub.

## Page grammar and MCP tools

The pages are filled by MCP responses, so every page is a generic rendering of tool results built only from the kit's components: a stats row, one table or list under a search and filter toolbar with row actions, a key/value detail with related lists, a form made of a tool's fields, and an action card for a pending write. Each screen names its tools in a muted second line under its caption, "Filled by: tool_a, tool_b". Tool names are the platform's where they exist and illustrative otherwise (the real ones are `agency_get_agency`, `agency_list_roles`, `agency_list_goals`, `actor_list_groups`, `actor_create_group`, `actor_join_group`, `actor_set_group_join_mode` and `ai_set_limits`).

## The console

Inside a hub every page has a header strip across the full width and three columns under it: the side bar on the left, the content area in the middle and the chat on the right. The header strip holds, from left to right, the brand (Hub Steward with the Demo chip), the hub switcher as a compact horizontal button (initials, agency name, state and kind), a divider, the breadcrumb without the agency name, and the language select. The hub switcher's panel drops down from it over the content. The side bar starts directly with the menu: Status, then these captions: Agency (Profile, Goals, Roles, Risks), Users & Agents (Users, Groups, Agents), Generated (Approvals, Operations, Farm orders, Produce, Equipment), Knowledge (Documents) and Settings (General, Models) under a divider line, and Sign out at the bottom. A caption with no page for the open agency is not shown. A page can have a sub-menu: Operations has Network, Activity, Alerts, shown under it while one of those pages is open and collapsed behind a small chevron otherwise. A count chip on a menu row (for example on Approvals) shows what waits for the manager. Hash routes are in `_generator/sitemap.py` and on the index; for example Status is `#/status`, Settings > Models is `#/settings/models` and Agents is `#/people/agents`.

## The chat and the landing rule

The chat is the right-hand column of every page, and it can be collapsed to a narrow rail with the chat icon, an accent dot for an unread reply and the same side-panel icon to open it again. It has a one-row header (the label "Chat", a context chip with the page's icon and label, and the collapse button, which uses the side-panel icon), a thread, and the chat box at the bottom: one rounded card with a text area of at least three lines on top and a toolbar below it, the attach button at the left and a round accent Send arrow at the right, with 16 px of space around it. There are no mode pickers or microphone. A model picker, a small chip with the model's label and a chevron after the attach button, is drawn whenever the hub has a model the chat can use, so the chat box says which model it is on even when there is only one; the label is whatever the admin typed for that model (the model's own name until then), which is what tells apart the same model from two providers; it opens a short list over the chat box with a tick on the person's choice. Before a hub has a model there is no picker. The chat starts on the first of those models in the Models list. The robot badge appears only on the assistant's messages in the thread.

On landing the page is the title, one primary button and the content; actions are visible by layout, never explained by text. The one filled accent button sits at the right end of the title row on every page; other actions are quiet buttons and row actions at the right end of their rows, and an empty state is a card with a short sentence and the primary button inside it. The chat is quiet on landing: a one-line greeting, the chat box and at most three suggestion chips. A conversation appears only in screens captioned "After asking: <prompt>", where tool calls are collapsed to one line ("Called 5 tools") unless the screen is about the calls.

The rule for every drawn conversation: every assistant turn ends with an action, a list or a form, and may navigate. Chat results that are content target the content area: a list or a form the chat produces is drawn in the content area under a banner "Answer to: <prompt>" with a 1 px accent border, and the thread shows only a compact reference card saying it is shown there. Approvals and actions stay in the thread, and a result can carry "Open <page>" buttons that navigate, so the page you move to becomes the conversation's context. Tool names in the drawings are illustrative except `agency_get_agency`, `agency_list_roles`, `agency_list_goals`, `actor_list_groups`, `actor_create_group`, `actor_join_group`, `actor_set_group_join_mode` and `ai_set_limits`, which exist in the platform. A muted note under a screen's caption, outside the window, says when its data is drawn for the page; nothing labelled "Example" appears inside a window.

## Themes

There are five themes, switched with one setting under General: Dark (the default), Light (warm paper), Midnight (blue-black, sky-blue accent), Forest (very dark green, soft green accent) and High contrast (pure black, white text, bright yellow accent). Every colour comes from a token, so a theme changes the whole window, and text and the filled accent button pass WCAG AA contrast in each. The chosen theme is saved in the browser's local storage under the key `theme`: on load the page reads it before the first paint and sets `data-theme` on the root element (the default is `dark`, and an unknown or unreadable value falls back to `dark`), and choosing a theme in General writes the key and switches at once. It is per person and device, not a hub setting, like the console's language (key `lang`). These drawn pages stay script-free, so they show a theme only when a page is built with it.

On General the settings are drawn as rows of a label and a control that shows its value, with a divider between rows.

## What exists today

The console holds one model per hub: a provider, a model name, a base address (Meta Model API and Other only) and the key. Hugging Face and Acme AI have fixed addresses, Meta Model API starts from its own, and Other (OpenAI-compatible) needs one the manager types; the console refuses an address that is not https or that points at a private or loopback host, and never returns the key. Several models per hub, the Models table with its "Used by" links and the Roles page with its model filter are a proposal: they need the hub to keep a list of models. The chat uses the hub's one model today; the checkbox "Can be used in the chat" on a model's page and the picker in the chat box are a proposal that needs each model to carry that flag. An agent's own model is chosen on its page (`people/agent-edit.html`), not on Models.

The Model dropdown is filled from live data: before the key is saved it shows the standard list (GLM-5.3 on Hugging Face; Lite 5.5, Core 5.5, Max 5.5 and Pro 5.1 on Acme AI; Muse Spark 1.3, 1.2 and 1.1 on Meta Model API, which are example names because Meta's are not recorded yet) under "Save the key to see every model it can use"; once the key is saved the console asks the provider's own list (the console's own endpoint, not an MCP tool: an OpenAI-compatible `GET /models` with the hub's key) and shows it as From your key above the standard list, with Other model... last and a Refresh models link; while it loads the dropdown reads "Loading models from" and the provider's name; when it cannot be read the standard list stays, with a note and Try again. The AI backend's maintained list (`ai_list_models`) arrives with the console's retirement.
