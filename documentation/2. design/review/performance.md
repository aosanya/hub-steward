Sources: a passage search compares the query with every passage in Go, and nothing bounds what it loads (read from code, not measured). `mwanachama-backend-sources/search.go` `SearchChunks` selects every chunk of one embedding model (and of one source when given) as whole rows, the vector included (`embedding` is a `json` column, `sources.blueprint.json`), decodes each into a float list, scores it in `cosine`, sorts all of them and keeps at most 50 (`MaxMatches`). The only index is `embedding_model`, so every search is a scan of that model's chunks. It grows with chunks held by the agency (a document of 40 pages is tens of passages; a lab library of a few hundred documents is thousands of vectors of some hundreds to a few thousand numbers each), and with every search a person or the agent makes. Because `specstore.List` is capped only when a host calls `CapLists` and `DefaultListCap` (100) is a constant nobody sets (`specstore/store.go` lines 177 to 191; no caller in wakala-api or sources), the load is unbounded; if a host ever sets the cap the search would instead rank only the first 100 unordered chunks and answer wrongly with no error. Then `withSources` calls `GetSource` and `standing` once per distinct source among at most 50 matches, and `standing` (`verification.go` line 54) loads the whole verification history of the source newest first just to read the first row. The fix is a vector index in the database (shared SRC4 / S-row for a vector field type) or a narrowing filter before the scan; a `limit 1` on `standing`. The module is mounted per agency (`wakala-api/internal/api/http/sources_routes.go`), so the search runs on the request. Open; build finding, no question until the owner says how many documents an agency is meant to hold.
